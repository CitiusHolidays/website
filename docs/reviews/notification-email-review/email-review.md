# Citius transactional emails

The approved branded emails use the real Citius logo, one clear event heading,
compact labelled details and one primary action. The small header labels have
been removed. Security notes, useful detail labels and the reply action remain.

These pictures show actual template output with fictional values. They are
browser renders, not Gmail, Outlook or delivered-mailbox evidence. No real
message was sent. All 52 pictures use native GitHub attachments, with no new
review PNG or generated JSON committed to the source tree.

## Links, privacy and delivery

The button and quiet fallback retain the exact action URL. Authentication keeps
its token and callback construction and its existing subjects. The complete
URL remains in plain text without becoming a long visible token URL in the
HTML. The plain-text regression still checks separate detail labels and values.
Contact has one reply action and no browser-button failure instructions.

CRM private notes, document details, leave reasons and cost price remain behind
portal authorization. Recipients, approval stages, controls, retries, replay
keys, provider pacing and cancellation keep their existing rules. Prepared
messages remain frozen before delivery; already prepared messages retain their
old content when retried. Contact keeps the submitted Reply-To address.

## Logo and rollout

The single required runtime asset is
`public/images/email/citius-logo-v1.jpg`, derived from the existing approved
`src/static/logos/logo.webp`. It is a 420 by 149 JPEG, 21,468 bytes, displayed at
140 by 50 with Citius Holidays alternative text. Its artwork is unchanged.
This product asset is separate from disposable review screenshots and reports.

The fixed first-party URL is
`https://www.citiusholidays.com/images/email/citius-logo-v1.jpg`.
A local production build and `next start` served the exact bytes at that path
without authentication. GET and HEAD returned 200 with `image/jpeg`,
`public, max-age=31536000, immutable`, `nosniff` and no Set-Cookie header.
This verifies the local built app, not the live production domain.

Before a separately approved rollout enables the revised mail renderer, publish
and verify the frontend asset at that first-party URL. Deploy the renderer only
after that check. Keep the versioned filename immutable; use a new filename if
the artwork changes. If a client blocks images, the alternative text and full
action remain available. No deployment or provider setting was changed here.
